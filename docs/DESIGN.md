## 1. 产品定位

**名称**：二人世界（代码 id：`duo`）
**一句话**：发一个链接，两个人在各自的手机或电脑上一起玩的小游戏合集。

目标场景决定了设计取舍：

| 场景 | 特点 | 设计对应 |
|---|---|---|
| 异地恋，开着微信语音/视频一起玩 | 各用各的设备，人在不同城市，语音在微信里 | 不做内置语音；所有游戏都能两台设备联机；全部延迟友好 |
| 窝在沙发上，各拿一部手机 | 同一个 Wi-Fi，可以直接说话 | 面对面也好玩；有声音的游戏建议只开一台手机的声音 |
| 等餐、排队的碎片时间 | 3–10 分钟，单手竖屏 | 竖屏优先；每局 3–15 分钟；随时能退出 |

设计原则：
1. **合作优先，较量为辅**：10 款里 9 款是合作或默契类，分数属于"我们"。较量类只有五子棋一款，配上"小赌约"添点乐子。
2. **延迟友好**：服务器在美国（服务器时区 PDT），国内两人之间的单向延迟经常在 150–250 ms（§7.6）。每款游戏都按自己的同步模型设计，不允许出现"两人必须在 100 ms 内同时按下"的玩法。
3. **打开即玩**：不用注册、不用下载，首屏要轻（§5.1 的体积预算），微信内置浏览器里能用。
4. **隐私**：房间只属于两个人，不公开、搜不到。照片和记录只在房间内可见，房间 30 天没人玩就自动清理，也可以一键删除。

### 1.1 入口简介（首页文案定稿）

- 标题：**和 TA 一起玩的小游戏**
- 副标题：发一个链接就能开玩 · 不用下载注册 · 异地也像坐在一起
- 简介（用于 `<meta name="description">` 和分享描述，≤ 80 字）：
  > 二人世界是专为两个人做的网页小游戏合集：你画我猜、一线牵、心有灵犀、深夜聊天卡……创建房间，把链接发给 TA，就能在各自的手机上一起玩。
- 三步说明：① 创建房间　② 把链接发给 TA　③ 一起挑个游戏
- 隐私一句话：不用注册 · 房间只属于你们俩 · 30 天不玩自动清理
- "什么时候玩"三张小卡：
  - 📞 **异地视频时**：开着微信视频，一人一部手机，像坐在一起。
  - 🛋 **窝在一起时**：比各刷各的手机更有意思。
  - ⏳ **等餐排队时**：一局几分钟，随时可以停。

## 3. 用户流程

```
首页 ─创建房间─▶ 房间（等 TA）─复制链接 / 邀请图─▶ TA 打开 /r/CODE ─填昵称─▶ 加入
                     │                                                  │
                     └──────────────▶ 房间大厅（两人都在）◀──────────────┘
                                        │ 任一方点游戏卡 = 发起提议
                                        ▼
                         对方点「好呀」（两人提议同一款时直接开始）
                                        ▼
                         游戏简介弹层（规则 + 设置）─ 两人都点「准备」
                                        ▼
                         同步倒计时 3-2-1（以服务器 startAt 对齐）
                                        ▼
                                     游戏中 ─掉线/切后台─▶ 暂停等 TA（60s）─超时─▶ 结算（中断）
                                        ▼
                         结算：再来一局（双方确认）/ 换个游戏 / 保存图片
```

其他入口：
- 首页点某张游戏卡 → 弹出这款游戏的简介（只读）→「创建房间玩这个」：建房后自动对这款游戏发起提议。
- 本机浏览器里已有房间（localStorage 有 token）→ 首页顶栏显示「回到我们的房间」。
- 第三个人打开链接 → "这个房间已经有两个人啦" +「自己建一个」。

## 4. 页面与布局

### 4.1 视觉规范

- 风格：暖色、圆润、带一点手绘感的扁平插画。主角是两只圆滚滚的小团子，被一根红线连着。这是品牌元素，贯穿 Logo、加载动画和一线牵。
- 颜色 tokens（CSS 变量）：

  | token | 值 | 用途 |
  |---|---|---|
  | `--bg` | `#FFF8F1` | 页面底色（奶油色）|
  | `--surface` | `#FFFFFF` | 卡片 |
  | `--ink` | `#2B2A35` | 正文 |
  | `--ink-2` | `#8C8798` | 次要文字 |
  | `--thread` | `#FF4D6A` | 主色：红线、主按钮、强调 |
  | `--thread-soft` | `#FFE3E8` | 主色浅底 |
  | `--mint` | `#2EC4A6` | 成功、"延迟友好" |
  | `--amber` | `#FFB020` | 提醒、"需稳定网络" |
  | `--night` | `#1E2140` | 夜间主题底色（深夜聊天卡、心跳节拍）|

- 玩家色 6 选 1（入座时选，默认房主珊瑚、TA 天蓝）：珊瑚 `#FF6B6B`、天蓝 `#4D9DFF`、薄荷 `#2EC4A6`、柠檬 `#FFC93C`、薰衣草 `#9B7BFF`、蜜桃 `#FF9A76`。两人不能同色，对方用掉的颜色置灰。
- 头像 6 选 1：🐰 🐻 🐱 🐶 🦊 🐧（MVP 用 emoji，之后换成团子插画）。
- 字体：系统字体栈 `-apple-system, "PingFang SC", "HarmonyOS Sans SC", "MiSans", "Microsoft YaHei", sans-serif`。**不加载中文 Web 字体**（文件太大）。标题 800 字重；数字用 `font-variant-numeric: tabular-nums`。
- 圆角：卡片 20px、按钮 999px（胶囊）、输入框 14px。阴影 `0 6px 20px rgba(255,77,106,.10)`。
- 动效：弹性曲线 `cubic-bezier(.34,1.56,.64,1)`，时长 180–300ms，并尊重 `prefers-reduced-motion`。
- 触控：可点区域 ≥ 44×44px；游戏画布 `touch-action: none`；`viewport-fit=cover` 加 `env(safe-area-inset-*)`。

- 任一方点「换一个」或关掉弹层，提议就取消，两人回到大厅。
- 标着「需稳定网络」的游戏，如果实测双人延迟 > 250ms，在准备按钮上方加一行琥珀色提示："你们现在的延迟有点高（310ms），可能会卡，要不要先玩默契类？"——仍然允许开始。

通用浮层由平台层实现，所有游戏共用：
- **规则（?）**：随时可看，不会暂停游戏。
- **倒计时**：3-2-1-开始！，对齐到 `startAt`。
- **掉线**：「TA 掉线了，等 TA 回来… 0:42」+「回大厅」。T3 实时游戏自动暂停，回合类暂停计时。

- 竖屏优先，所有游戏在 360×640 下都必须能玩。横屏时把竖屏舞台居中显示，不强制旋转。
- 微信内置浏览器：

## 5. 技术架构

### 5.1 技术选型

| 层 | 选择 | 理由 |
|---|---|---|
| 语言 | TypeScript，前后端共享 `shared/` | 规则和物理只写一份：服务器用它做权威校验，客户端用它做预测和回滚，必须是同一份实现 |

| 构建 | 前端 Vite；服务端用 esbuild 打成单文件 | 部署产物只有 `web/` 静态文件和一个 `server.js` |
| 测试 | Vitest（单元/模拟）+ Playwright（双浏览器 E2E） | 见 §10 |

体积预算（gzip）：首页 JS ≤ 60 KB、CSS ≤ 15 KB；每款游戏按路由懒加载，单个游戏 chunk ≤ 80 KB；不打包大位图，插画用 SVG。

### 5.3 游戏模块接口

共享/服务端（纯函数，便于测试，也便于推理并发）：
```ts
type Seat = 0 | 1;
interface GameDef<S, A, V> {
  id: GameId;
  meta: GameMeta;                      // 名称、一句话、规则、时长、标签、网络等级、默认设置
  init(opts: Settings, ctx: Ctx): S;   // ctx 含 seed、serverNow、两人资料
  apply(s: S, seat: Seat, a: A, ctx: Ctx): { s: S; events?: Evt[]; error?: ErrCode };
  onTimer?(s: S, timerId: string, ctx: Ctx): { s: S; events?: Evt[] };  // 截止时间到
  view(s: S, seat: Seat): V;           // 按座位裁剪：绝不把对方的秘密（答案、谜底、地图）发给不该看的人
  result(s: S): GameResult | null;     // 返回非 null 即结束
  realtime?: 'relay';                  // 只有 T3 游戏：服务器转发 rt 帧（§7.2）
}
```
客户端：
```ts
interface GameClient<V> {
  mount(el: HTMLElement, api: GameApi): void;  // api.send / api.onView / api.onEvent / api.serverNow / api.rt
  unmount(): void;
}
```
平台层负责提议、简介、准备、倒计时、暂停、退出、结算和记录；游戏模块只管规则和舞台。

### 5.4 身份与房间

- 没有账号。第一次打开时在 localStorage 生成本机资料 `duo.profile = {nickname, avatar, color}`。
- 建房 `POST /api/rooms` 返回 `{code, seat: 0, token}`；入座 `POST /api/rooms/:code/join` 返回 `{seat: 1, token}`。token 是 128 bit 随机数（base64url），存在 `duo.token.<code>`；服务器只存 `sha256(token)`。
- 房间码 6 位，字母表 `23456789ABCDEFGHJKMNPQRSTUVWXYZ`（去掉了 0/O/1/I/L），显示成 `K7P·QM2`。
- 房间就是"我们的空间"：保存双方资料、战绩、画廊、自定义词库/题库、问答本。**30 天没有活动自动删除**（包括图片）。⚙ 里的「解散房间」任一方都能操作（二次确认，对方会收到通知）。
- 两个座位坐满后不再接受新人。**换设备**：⚙ →「生成换设备链接」（一次性，10 分钟有效）→ 在新设备打开即接管原座位，旧 token 作废。
- 服务器重启：房间元数据在 SQLite 里，链接照样有效；正在进行的对局会丢失，两人回到大厅并看到提示"服务器刚刚重启，这局没保存"。

### 5.5 HTTP API（前缀 `BASE_PATH/api`）

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/rooms` | 建房，body `{profile}` → `{code, seat, token}`；每个 IP 每小时 10 次 |
| GET | `/rooms/:code` | 公开元信息 `{exists, full, host: {nickname, avatar}, hostOnline}`，不含其他数据 |
| POST | `/rooms/:code/join` | 入座 `{profile}` → `{seat, token}`；满员返回 409 |
| POST | `/rooms/:code/rebind` | 兑换换设备链接 |
| POST | `/rooms/:code/images` | 上传拼图照片（需 token；≤ 2 MB；JPEG/PNG/WebP，服务器校验文件头魔数）→ `{imageId}` |
| GET | `/rooms/:code/images/:id` | 取图（需 token，`Cache-Control: private`）|
| GET | `/rooms/:code/gallery` | 画廊列表（需 token）|
| DELETE | `/rooms/:code` | 解散房间（需 token）|
| GET | `/health` | 健康检查 |

token 一律放在 `Authorization: Bearer` 里，不放 URL。

### 5.6 WebSocket 协议（`BASE_PATH/ws`）

连上后第一条消息必须是 `hello`（token 不放 URL，免得进 nginx 日志）。消息是 JSON 文本帧，T3 游戏的 `rt` 帧用紧凑数组。

客户端 → 服务器：

| t | 字段 | 说明 |
|---|---|---|
| `hello` | `code, token, v` | v = 客户端版本；版本不兼容时服务器回 `err VERSION`，前端提示刷新 |
| `ping` | `c, rtt` | c = 客户端单调时钟毫秒；rtt = 上一次测得的往返时间（服务器据此算双人延迟）|
| `act` | `aid, a, seq?` | 房间或游戏动作。aid = uuid，用于幂等；seq = 客户端看到的状态版本，需要时做过期检查 |
| `rt` | `[f, bits]` 或 `[f0, b0, b1, …]` | 实时输入帧，服务器只转发 |
| `cur` | `k, x, y` | 可丢消息：光标、拖拽中位置、托盘位置 |
| `react` | `e` | 表情飘屏 |
| `chat` | `text` | 聊天，≤ 200 字 |
| `vis` | `hidden` | 页面切到后台 / 回到前台 |

服务器 → 客户端：

| t | 字段 | 说明 |
|---|---|---|
| `welcome` | `seat, now, room, game?` | 全量快照，含当前游戏的本座位视图 |
| `pong` | `c, s` | s = 服务器 `Date.now()` |
| `ack` | `aid, ok, err?` | 动作结果 |
| `room` | `seq, room` | 房间视图：成员、在线、提议、准备、阶段、startAt… |
| `game` | `seq, view` | 本座位的游戏视图（回合类整包下发，体积很小）|
| `evt` | `seq, e` | 增量事件：笔画、拼图移动、揭晓… |
| `rt` | 同上 | 对方的实时帧 |
| `net` | `rtt: [r0, r1], pair` | 每 3s 一次；pair = 双人单向延迟估计 |
| `presence` | `seat, online, away` | 上下线、切后台 |
| `err` | `code, msg` | 见下 |

错误码：`ROOM_NOT_FOUND` `ROOM_FULL` `BAD_TOKEN` `REPLACED`（同一座位在别处打开了）`VERSION` `NOT_YOUR_TURN` `STALE`（seq 过期）`LOCKED`（拼图被对方拿着）`INVALID` `RATE_LIMITED`。

### 5.7 房间状态机

```
waiting(1/2) ──TA 入座──▶ lobby
lobby ──任一方点游戏──▶ proposed{gameId, by}
proposed ──对方「好呀」，或两人提议同一款──▶ intro{gameId, settings, ready: [false, false]}
proposed ──「换一个」/ 发起人取消──▶ lobby
proposed ──另一方提议别的游戏──▶ proposed{新 gameId, by: 另一方}   （后到覆盖，横幅显示"TA 改成了 X"）
intro ──两人都 ready──▶ countdown{startAt}
countdown ──到点──▶ playing
playing ──有人掉线 / 实时游戏中切后台──▶ paused{seat, deadline}
paused ──人回来了──▶ countdown ──▶ playing
paused ──60s 超时──▶ result{aborted}
playing ──result() 非空 / 有人退出──▶ result
result ──两人都点「再来一局」──▶ intro（沿用设置）
result ──「换个游戏」──▶ lobby
```
所有状态迁移只在服务器上发生。客户端只发意图（`act`），按服务器下发的 `room` 渲染。

## 6. 并发设计

### 6.1 服务器层面：很多对情侣同时在线

- **单进程，每个房间串行**：Node 是单线程的。每条消息的处理（校验 → 纯函数 apply → 广播）一次同步完成，中间没有 `await`，所以同一房间内天然没有竞态，不需要锁，房间之间也互不影响。需要 I/O 的事（写 SQLite、图片落盘）都放在状态更新之后异步做，而且不回写状态。
- **计时器**：每个房间用 `setTimeout` 管自己的截止时间，不跑全局 tick，空闲的房间不占 CPU。
- **容量估算**：
  - 回合类：每个房间 < 1 条消息/秒。
  - 你画我猜：笔画约 25 条/秒。
  - 一线牵：每人每秒 60 帧，每个房间约 120 条/秒的转发。
  
  单核 Node + ws 每秒能处理几万条小消息。按这台 1 核机器保守估计，能同时撑住约 100 个实时房间加上千个回合类房间，远超需求。所以不做多进程或多机，但 `RoomManager` 接口要保持干净，以后真要扩容，按房间码哈希分片即可。
- **消息分级**：
  - 必达：`act`、`evt`、`game`、`room`、`rt`，按顺序发送，绝不丢。
  - 可丢：`cur`（光标、拖拽中位置、托盘位置）和 `react`，只保留最新一条。某个连接的 `ws.bufferedAmount > 256 KB` 时，暂停给它发可丢消息。
- **限流**（每个连接一个令牌桶）：`act` 20/s、`cur` 30/s、`rt` 120/s、`chat` 2/s、`react` 2/s。超限就丢弃，并回 `RATE_LIMITED`（`rt` 超限只丢不回）。单条消息 ≤ 16 KB，图片走 HTTP。
- **内存上限**：你画我猜每轮笔画日志 ≤ 2 MB，超出后拒绝新笔画并提示。空房间 10 分钟后从内存卸载，数据留在 SQLite。

### 6.2 房间内并发：两个人同时操作

| 场景 | 处理方式 |
|---|---|
| 两人同时点了不同游戏 | 提议只有一个槽位，后到的覆盖前一个，成为新提议；两人提议同一款时直接进入简介 |
| 两人同时点「好呀」和「换一个」 | 服务器按到达顺序处理；第二个动作因为状态已经变了，成为 no-op（回 ack ok，不报错）|
| 两人同时作答（心有灵犀 / 你懂我吗） | commit-reveal：答案先存在服务器，对方的视图里只有"TA 已作答"；两人都提交后统一揭晓 |
| 两人同时拿同一块拼图 | 服务器加锁 + 3s 租约，先到先得；后到的人收到 `LOCKED`，本地把那块弹回原位，提示"TA 正拿着这块" |
| 回合制里抢先操作（五子棋落子、聊天卡翻牌） | 校验 `turn`；客户端带上 `seq`，服务器状态已经前进时回 `STALE`，客户端用最新快照重绘 |
| 需要两人都同意的事（悔棋、再来一局、"算我们一样"、小约定、解散） | "提议—确认"（`shared/consent.ts`）：服务器保存 pending 请求，等对方确认或拒绝；发起方做出任何新动作，请求自动撤销 |
| 时间到的那一瞬间猜中 / 落子 | 以服务器收到的时间为准，`deadline + 400ms 宽限` 内有效，之后回 `INVALID`。先被处理的那个生效；回合结束事件是幂等的 |
| 网络重发导致同一个动作到了两次 | 每个 `act` 带 `aid`，服务器为每个座位保留最近 200 个 aid，重复的直接回上一次的 ack |
| 同一个人开了两个标签页或两台设备 | 一个座位同一时刻只允许一条连接。新连接 `hello` 成功后，旧连接收到 `err REPLACED` 并被关闭，旧页面显示"已在其他页面打开" |

### 6.3 顺序与一致性

- 每个房间有一个单调递增的 `seq`，每次状态变化 +1；`room`、`game`、`evt` 都带 seq。
- 客户端按 seq 顺序应用。发现跳号（只可能出现在重连边界）就丢掉增量，等服务器的 `welcome` 全量快照。
- 乐观更新：客户端可以先把自己的动作渲染成"待确认"状态（半透明或转圈），收到 `ack ok` 后转正，收到 `ack` 失败就回滚并弹 toast。

### 6.4 掉线、重连、切后台

- 心跳：客户端每 2s 发一次 `ping`；服务器 10s 收不到任何消息，就认为这个座位掉线（`presence online:false`）。
- 断线后客户端自动重连，退避 0.5s → 1s → 2s → 4s（上限 5s）。重连成功后发 `hello`，服务器回 `welcome` 全量快照。
- 房间座位一直保留。对局层面：回合类游戏最多暂停计时 60s，实时类游戏立刻暂停；60s 内没回来，这局按"中断"结算，回到大厅。
- 切后台（`visibilitychange`）时发 `vis hidden`：
  - 实时类（一线牵、颠颠爱心）立即暂停，人回来后 3-2-1 继续。
  - 心跳节拍不暂停，按时间轴继续，回来直接跳到当前位置。
  - 回合类不受影响，对方只看到"TA 暂时离开了"。
- 刷新页面等于一次重连，体验和掉线一样。

## 7. 延迟设计

### 7.1 测量与展示

- **时钟同步**：客户端发 `ping{c}`，服务器回 `pong{c, s}`，客户端在 `t3` 收到：`rtt = t3 − c`，`offset = s + rtt/2 − t3`。保留最近 8 个样本，取 rtt 最小那个样本的 offset（抗抖动）。`serverNow() = performance.now() + offset`。开局前 3 秒每 250ms ping 一次以便快速收敛，之后每 2s 一次。
- **双人延迟**：A 发给 B 的消息走 A → 服务器 → B，单向约等于 `rttA/2 + rttB/2`。服务器每 3s 下发一次 `net{rtt: [rA, rB], pair}`。
- **展示**：大厅情侣条和游戏 HUD 显示 `pair`：🟢 < 120ms · 🟡 120–250ms · 🔴 > 250ms 或最近 5s 内重连过。点开能看详情（我的延迟 / TA 的延迟）。
- **调试**：URL 加 `?debug=1` 显示调试浮层：rtt、offset、pair、回滚次数和最大回滚帧数、停顿次数、输入延迟帧数。

### 7.2 五种同步模型

| 等级 | 模型 | 适用 | 做法 |
|---|---|---|---|
| T0 | 回合制 | 深夜聊天卡、爱心五子棋 | 服务器权威；客户端先乐观显示"待确认"；延迟只影响确认快慢 |
| T1 | 同时提交，统一揭晓 | 心有灵犀、你懂我吗 | 服务器暂存答案，对方视图里只有"TA 已作答"。两人都交了，服务器下发 `revealAt = now + 800ms`，两端在同一时刻翻牌——开着视频的两个人能同时"哇"出来 |
| T2 | 流式 + 服务器裁决 | 你画我猜、你是我的眼、拼出我们 | 自己的操作本地立即显示。连续量（笔画、拖拽、光标）按 20–25Hz 批量发送，对方用 100–150ms 的插值缓冲平滑播放。冲突和判定（猜词、撞墙、锁、吸附）只由服务器做 |
| T3 | 实时物理 | 一线牵（回滚）、颠颠爱心（击球者权威） | 细节见 GAMES.md。一线牵：确定性整数模拟 + 预测对方输入 + 回滚重算。颠颠爱心：任何时刻只有"该接球的人"能改变爱心轨迹，轨迹是确定性函数，对方收到击球事件后快进 |
| T4 | 本地判定 | 心跳节拍 | 两端在同一个服务器时刻起播，判定完全在本地按音频时钟做；网络只传判定结果，延迟只影响"对方的特效"什么时候出现 |

### 7.3 延迟预算

| 游戏 | 舒适 | 可玩上限 | 超过上限时的表现 |
|---|---|---|---|
| 深夜聊天卡 / 五子棋 / 心有灵犀 / 你懂我吗 | 任意 | 2s | 只是确认和揭晓变慢 |
| 你画我猜 | < 300ms | 1s | 画面晚到；合作计分，不影响公平 |
| 你是我的眼 | < 200ms | 500ms | 行者移动有顿挫（180ms 动画能掩盖一部分）|
| 拼出我们 | < 200ms | 500ms | 对方手里的拼图移动不够顺；抢同一块时弹回得更晚 |
| 心跳节拍 | 任意 | 任意 | 对方的特效晚到，判定不受影响 |
| 颠颠爱心 | < 200ms | 350ms | 对方击球时，爱心会在托盘上短暂停一下 |
| 一线牵 | < 120ms | 250ms | 对方角色的修正变多；> 300ms 时会短暂停顿，并提示"网络卡顿" |

### 7.4 延迟友好的玩法设计（所有游戏都要遵守）

1. 不设计"两人必须在 X 毫秒内同时按下"的判定。需要两人配合的地方，用**状态**（站在压板上、抓住墙）代替**瞬间**（同时起跳）。
2. 接力类玩法（颠颠爱心）在两次交接之间留足飞行时间（≥ 0.8s），让延迟藏在飞行里。
3. 优先合作计分：延迟不应该决定谁赢。唯一的较量游戏（五子棋）是回合制。
4. 所有"一起看到"的时刻（倒计时、揭晓、翻牌）用服务器时间戳 `startAt / revealAt / flipAt` 对齐，而不是"收到消息就播放"。
5. 计时器一律以服务器为准，客户端显示 `deadline − serverNow()`，服务器给 400ms 宽限。

### 7.5 弱网降级

- 大厅里每张游戏卡按当前 `pair` 显示"网络 ✓"或"可能会卡"（T3 游戏的阈值是 250ms，T2 是 500ms）。
- 对局中 `pair` 连续 5s 超过上限时，HUD 网络图标变红，并提示一次；不强制中断。
- 一线牵的输入延迟和最大回滚帧数随 `pair` 自适应（见 GAMES.md）。

### 7.6 服务器位置的影响（重要）

现有 VPS 在美国（服务器时区 PDT）。国内用户到它的 RTT 通常在 150–220ms，所以双人单向延迟在 150–250ms，正好落在一线牵"可玩上限"附近。以上设计已经保证在这种最坏情况下所有游戏都能玩。以后想让一线牵和颠颠爱心手感更好，有两条路：
- 首选：把游戏服务（只是一个 Node 进程）部署到离两人更近的节点（香港、日本或国内），前端仍然可以放在原站。
- 备选（M4 之后，可选）：一线牵和颠颠爱心的 `rt` 帧改走 WebRTC DataChannel 点对点，服务器的 WS 只做信令，STUN 用自建的或国内可达的公共 STUN；打洞失败时自动回落到 WS 中转。国内移动网络里对称 NAT 很多，不能依赖 P2P 一定成功。

## 8. 数据与隐私

SQLite 表（`DATA_DIR/duo.db`）：
- `rooms(code PK, created_at, last_active_at, seat0_token_sha, seat1_token_sha, seat0_profile, seat1_profile, settings_json)`
- `matches(id, room_code, game_id, started_at, ended_at, result_json)`：战绩、默契值
- `gallery(id, room_code, kind, created_at, meta_json, file)`：你画我猜的画（存笔画 JSON，缩略图由前端渲染）、拼图成品、心有灵犀词链
- `custom_content(id, room_code, kind, author_seat, data_json)`：自定义词、自定义题
- `journal(id, room_code, kind, created_at, data_json)`：聊天卡的问答本和收藏、小约定
- 图片文件：`DATA_DIR/rooms/<code>/<imageId>.jpg`

规则：
- 不收集手机号或邮箱。
- 日志里不记录 token、聊天内容和答案。
- 房间 30 天无活动，后台任务删除（包括文件）；「解散房间」立即删除。
- 所有用户输入都按纯文本渲染，不插入 HTML。长度上限：昵称 12、聊天 200、猜词 30、自定义词 20、自定义题 60。

## 9. 部署（交付时执行，事先要用户确认）

- 生产机现状：1 核、约 900 MB 内存；**2026-10-23 写这份文档时根分区已经 100%（只剩约 43 MB）**。部署前必须先把磁盘清出空间——这件事单独处理，不在本项目范围内。`node_modules` 和 Playwright 浏览器用完即删，或者在别处构建好只拷贝产物。
- 进程：systemd `duo-games.service`，`ExecStart=/usr/bin/node --disable-warning=ExperimentalWarning /opt/duo-games/server.js`，`MemoryMax=200M`，`Restart=always`，用非 root 用户运行；环境变量 `PORT=8790 BASE_PATH=/duo/ DATA_DIR=/var/lib/duo-games`。端口只监听 127.0.0.1。
- nginx：挂在现有站点的子路径下，或者用独立子域名，由用户二选一（`BASE_PATH` 可配置）。示意：
  ```nginx
  location /duo/ws   { proxy_pass http://127.0.0.1:8790; proxy_http_version 1.1;
                       proxy_set_header Upgrade $http_upgrade; proxy_set_header Connection "upgrade";
                       proxy_set_header X-Real-IP $remote_addr; proxy_read_timeout 120s; }
  location /duo/api/ { proxy_pass http://127.0.0.1:8790; client_max_body_size 3m; }
  location /duo/     { root /opt/duo-games/web-root; try_files $uri /duo/index.html; }  # 带 hash 的资源 expires 1y
  ```
- 注意：现有站点的 nginx 对每个客户端限流 10 r/s（burst 40），而且静态资源也算在内。所以要么给 `/duo/` 单独一个不套这个 zone 的 location，要么控制首屏请求数（合并 Vite 产物，首屏 ≤ 10 个请求）。

## 10. 测试与验收

- **单元测试（Vitest）**：覆盖每款游戏 `rules.ts` 的 init / apply / view / result。
  - **视图裁剪测试**：遍历每个阶段，断言 `view(s, seat)` 里不含对方的秘密——你画我猜的谜底、你懂我吗和心有灵犀未揭晓的答案、你是我的眼行者视图里的墙和陷阱。
- **并发测试**：在同一个事件循环轮次里，让两个座位提交冲突动作（同时提议、同时抢锁、同时作答、截止瞬间猜中），断言结果唯一，而且两端视图一致；aid 重放是幂等的；覆盖 `STALE` 路径。
- **一线牵确定性**：
  - 同一个种子 + 同一串输入跑两遍，每一帧的 hash 都相同。
  - 随机输入跑 10 万帧，不出现 NaN 或越界。
  - `sim.ts` 用 lint 规则禁止 `Math.random/sin/cos/tan/atan2/pow/exp/log/sqrt`（开方用 `shared/fixed.ts` 的 `isqrt`）和非整数字面量。
- **网络模拟**：在 Node 里起两个虚拟客户端加一个中转，用虚拟时钟注入单向延迟 50/150/250/400ms、抖动 ±40ms，断言：
  - 一线牵两端在已确认帧上的 hash 一致；同时记录回滚帧数分布和停顿次数。
  - 颠颠爱心两端的击球序列一致。
  - 拼图锁竞争的结果在两端一致。
- **E2E（Playwright，两个浏览器上下文 = 两个人）**：
  - 主流程：建房 → 入座 → 每款游戏的冒烟流程 → 结算 → 再来一局。
  - 弱网：用 `?lag=200&jitter=40` 再跑一遍。
  - 异常：掉线重连（`context.setOffline`）；同一个 token 开第二个页签，触发 `REPLACED`；第三个人进来看到满员页。
- **延迟注入**：前端 `?lag=150&jitter=30` 在 transport 层给收发两个方向都加延迟（保持消息顺序）；服务端环境变量 `DUO_LAG_MS` 同理。这是验收延迟设计的主要手段。
- **设备手测清单**：iPhone Safari、Android Chrome、微信内置浏览器（iOS 和 Android）、桌面 Chrome；其中一人用 Wi-Fi、一人用 4G。
- **性能**：中端安卓机上，一线牵和颠颠爱心稳定 60fps（含最坏情况 20 帧回滚，单帧模拟 + 渲染 ≤ 8ms）。
